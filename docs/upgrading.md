# Upgrading an existing membrAIn project

Use this optional procedure only when an upgrade is requested. Reading newer guidance does not apply it to an existing project. The project's current instructions govern the review and any edits; stop and explain conflicts affecting the work rather than silently choosing a rule.

## Establish the comparison

1. Read the target project's entry point, agreements and relevant current memory. Inspect its branch and working tree; preserve unrelated and uncommitted work.
2. Identify the requested target foundation version and obtain its actual files. Record the source revision when available and distinguish a release from an unreleased candidate. Disclose unavailable access rather than claiming a current upstream check.
3. Establish the adopted baseline from an existing provenance note, retained Git history or other evidence. If uncertain, say so. A matching paragraph or version label alone does not establish full adoption. Compare available files directly and identify uncertain origins instead of inventing a baseline.
4. Review the relevant differences between the original foundation, the target project's current files and the proposed foundation. Include entry-point adapters, referenced procedures and safeguards when affected; do not copy over unrelated project content.

## Propose before applying

Classify each meaningful difference as a foundation improvement, a local choice to preserve, or an unresolved conflict. Show the proposed changes and their reasons, including any omitted foundation changes. Routine wording changes may be grouped; changed permissions or responsibilities must remain explicit.

Preserve local roles, authority, branch and deployment workflows, acceptance arrangements and project-specific constraints. Never infer broader authority from a new example. Preserve the purpose of existing entry points and their links; do not create competing sources of truth or copy the uninitialised START template over a working project.

Obtain agreement on meaningful changes before adoption. If the owner already approved an exact reviewed change set, apply that authority without asking again. An instruction to compare or plan an upgrade does not authorise edits. Commit, push and release authority remain governed by the target project.

## Apply and verify

Apply only the agreed changes. Check the diff, local links, entry-point routing, preserved safeguards and affected current-state statements. Use a focused fresh-reader exercise if the routing or behaviour changed; report checks actually performed and their limits.

After adoption, update one concise foundation-baseline note in the existing Project choices section of the agreements. For example: “Foundation baseline: membrAIn [verified release/revision]; local delivery and role agreements retained; [material exclusions, if any].” Fill this with actual evidence; do not create empty fields or report an incomplete adoption as complete. For a partial upgrade, retain the prior baseline and identify the adopted changes rather than implying full compliance with a new version.

Report changed files, remaining conflicts or exclusions, validation and whether the update is local or shared. Do not automatically upgrade other projects, add synchronisation or rewrite their application code.

## Example comparison

An older project assigns implementation to one agent and review to another, and grants publishing permission only to its development branch. A newer foundation provides generic maintenance guidance and permits flexible roles.

| Difference | Classification | Proposed treatment |
| --- | --- | --- |
| Replace accumulated current-state history with a concise snapshot | Foundation improvement | Propose the maintenance guidance; preserve historical evidence. |
| Named implementation and review responsibilities | Local choice | Retain them; generic flexibility is not a request to change roles. |
| Standing development-branch publishing permission | Local choice | Retain the exact scope and exclusions; do not extend it to production. |
| Earlier adopted version cannot be established | Unresolved provenance | State the uncertainty and review the available files directly. Do not invent a version. |

This is illustrative. Actual adoption requires inspecting the target project and reviewing its own differences.
